# 製作工程

これは[Reading Pack制作標準](../spec/reading-pack-production-standard.ja.md)を`reading-pack`参照実装で運用するための公開ガイドである。完成するMarkdownの形式は[Reading Pack形式仕様](../spec/reading-pack-format-spec.ja.md)が別に定める。ここにあるcommand名、file名、session、transactionはtoolkit固有であり、第三者が制作適合を宣言するための必須実装ではない。

読解パックはW0からW13までの工程で作る。各工程には安定したID、実施主体、出力、通過条件がある。Dは再現可能な処理、Lは検査を伴う任意のモデル支援、Hはソフトウェアに代行させない人間の判断を表す。Rは、氏名付きの人間または監査記録付きAIによる候補の一次レビューである。

## W0 — 設計制約を決める（H）

`quality-plan.json`で用途別プロファイルを選び、対象範囲、責任者、ネタバレ方針、書籍の性格、想定読者、利用できる権利、言語、公開する派生物、容量上限、機密境界、実測値の下限、再構築不能性の判定基準を記録する。

既存パックを置き換える場合は、比較資料をハッシュへ結び付け、`content_floor`に現行版を下回ってはならない項目別の指標を宣言する。品質プロファイルへの適合には、公開上の必須条件をすべて満たす必要がある。各条件に検査または人間の確認手順があることを確かめ、`design_constraints = approved`とする。責任者の承認は、後で現在の品質計画と正本データの両方へ結び付ける。

生成前には、著者、編集者、出版社、権利者から提供される資料も棚卸しする。構造化済みの章、要約、命題、Q&A、本書固有方針、人名、用語、参照先があれば、Author Input Packageで各項目を`provided`、`augment`、`generate`、`omit`のいずれかに指定する。record単位の`source_locations`には、module原資料のhashとは別に、提供または検証済みのlocatorを保持できる。本文を含まない適用計画を確認してから、`draft`として正本へ入れる。未構造化の付録を添付しただけでは、正本の項目へ自動変換しない。詳しくは[Author Input Package](author-input.ja.md)にある。

## W1 — 書誌を確定する（D → H）

書名、著者、出版社、刊行日、ISBN、公式URL、権利者を`reading-pack.toml`と言語別データへ記録し、公式の刊行情報と照合する。

## W2 — 確実性区分を定める（L → H、任意）

著者が採用する証拠の種類によって区分する。定義を意味の損失なく保ち、数値化した信頼度へ変換しない。この枠組みを持たない書籍では省ける。

## W3 — 章節地図を作る

- W3a（D）：`import-plan`がMarkdown、Org mode、EPUB3、PDF、プレーンテキストから、本文を含まない階層、所在、抽出確度、来歴、診断、判定結果を作る。正本は変更しない。PDFではローカルのPopplerを任意で使い、結果は必ず人が確認する。
- W3b（D → H）：構造案を確認し、競合を解消して`import-apply`を実行する。協調ロックのなかで原資料と正本の現在状態を再検査し、下書きの構造だけを書く。再取込みの対応が曖昧な場合や、計画後に状態が変わった場合は停止する。
- W3c（D → H）：紙面ページは刊行版と照合できた場合だけ加える。電子版だけの書籍は章節見出しで案内する。
- W3d（L → D → R）：構造化入力のない書籍では、再開可能な`work plan/next/ingest/close/status/retry/finalize` sessionを使い、章・moduleごとの上限付きresponseから通常のcandidate runを作れる。0件の結果も明示して記録し、既存の原資料根拠検査、work ledger、候補レビュー、`draft`だけの適用経路を再利用する。確認者は内容ハッシュへ結び付いた候補IDを一件ずつ採用し、その候補だけを`draft`として適用する。章候補には、論証の展開、事例、比喩、文体、段落ごとの内容を含めない。用語説明は原資料の定義文を引用・微修正せず、本書内の意味を500字以内で抽象的に要約する。response取込み時にも長さと原資料の連続複製を検査し、違反したwork itemは保存せず再生成へ戻す。
- W3e（L → D → R、任意）：初回下書きの適用後、`work plan --purpose coverage`で、固定の`whole_book_gap_audit_v1` rubricとhashへ結び付いた現行正本を使い、選択した全章・module scopeを監査する。各scopeは、根拠付きの改善候補または明示的な0件結果を残す。projectから自由記述promptを注入したり、record件数のquotaを課したりせず、要約、用語、命題、索引説明の欠落と実質的な弱さを点検する。既存の用語説明に原資料の連続複製があれば、0件結果ではscopeを終了できず、同じIDの抽象的な要約を改善候補として返す。これによりAIPの`provided`入力も自動承認せず通常の候補経路へ戻す。人名・用語の高recall発見はW5/W6の原資料照合付きcatalog経路を使う。
- W3f（D、任意）：確認済みの明示的normalized-text章mapがある場合は`work plan --chapter-map`へ渡す。mapはsession IDの一部となり、章scopeの根拠が対象span外にあればcandidate finalizeまで待たずingestで拒否する。

PDFとEPUBの照合用表現は、指定した原資料から内部で導出する。任意の抽出テキストで差し替えない。

## W4 — 正準命題を作る（D → H、任意）

安定ID、記述／規範の区分、種別、章参照、確実性区分、反証条件または再検討条件を管理する。JSONから機械的に生成するが、命題の文言と確実性は著者が判断する。

## W5 — 人名索引を作る（L → D → H、任意）

登録済みの原資料へ`catalog extract`を実行し、非公開の人名抽出台帳を作る。組込みの認識処理が出すのは保守的な種候補であり、網羅的な固有表現抽出ではない。見落としと誤検出の両方がありうる。

人名の出現位置が、ハッシュを確認した一つの章範囲内に定まった場合だけ候補にできる。章題の順序から推定した対応は`review_required`のままとし、人が確認した章対応を再入力するまで人名と用語の候補化を止める。モデルや固有表現抽出器の結果を`catalog candidates --responses`で加えることもできるが、追加した名前は指定章の正確な根拠内に存在しなければならない。

候補が0件でも、その章に人物がいないとは判定しない。作業台帳には未確認の欠落として残す。採録後は`catalog context-plan`で説明のない全人名を列挙し、`catalog context-candidates`で`book_context`の更新候補を作る。説明には、その人物が本書で何者として紹介され、どの見解、仕事、引用、評価に結び付くかを一文で記す。一般的な人物紹介や「同章で言及」という仮文では代用しない。

複数のrunを順次`draft`適用した場合は、`candidates receipt`で適用順の一つの引き渡しartifactを作る。新manifestはCASの正確なbefore/after hashを残すため、隣接runと現行正本への連続を検証できる。旧runは明示的な部分連続modeが必要で、未検証linkとして残す。

## W6 — 用語の所在を作る（D → H、任意）

同じ抽出台帳から主題用語と、最初の実質的な説明箇所を提案する。明示的な定義や命名があれば、まえがき、目次、章予告での先行言及より優先する。定義の手がかりがなければ、最初の章内出現へ戻る。

引用付き定義や頭字語の形は発見の手がかりにすぎず、用語集へ採録すべきことの証明にはならない。人が誤検出、見落とし、表記、説明箇所を確認する。採録後は`book_meaning`へ、一般辞書の定義ではなく本書内での意味や役割を500字以内の抽象的な要約として記録する。原資料の文をそのまま、または軽く直して掲載しない。

## W7 — 誤読と訂正を記録する（L → H、任意）

誤読と、単独で意味が通る短い訂正を記録する。訂正は通信なしでも機能し、必要なら公式ページを併記できる。秘密の評価プロンプトや長い本文は含めない。

本文だけから訂正を推測するより、独立して管理する著者Q&Aを優先する。`sources plan`と`sources apply`で原資料を登録し、`qa plan`を実行する。各項目は安定IDの下に「批判」「本書への影響」「本書の応答」「残る不確実性」の四項目を持つ。

構造化JSONでは種類を明示できる。付録形式のOrgでは`QA_TYPE`または人が確認した`qa classify`の対応表を使う。分類されていない批判は未解決のまま残し、自動的に「誤読」と呼ばない。短く編集済みのQ&Aはそのまま候補化できる。長いQ&Aは四項目を丸ごと転記せず、分類済み計画の全項目に対応した短い候補と、同じ項目内の正確な根拠を入力する。どちらも長文複製の検査、候補の一次レビュー、著者承認を省略しない。

## W8 — AIへの指示を確認する（H）

ローカルのテンプレートと生成される`SYS`を確認する。出典の扱い、記述と規範の分離、確実性を順位へ変えないこと、対称的な検証、引用と再構築の禁止、所在案内の前提、参照先からの指示注入、著者のなりすまし、未許諾翻訳、初回の定型応答を点検する。

提供主体が参照先を公式補完資料とした場合は、正本referenceへ閉じた関係、URLまたはprefixの範囲、積極参照方針を宣言する。生成処理はそこからmodel非依存のREF metadataとSYS規則を加える。`book.official_url`だけでは積極参照を有効にしない。

## W9 — 参照資料を確認する（D → H）

索引工程は、原資料に明示されたHTTP(S) URLとDOIを参照先候補として抽出できる。安定IDと公式URLを使う。基本検査は通信に依存せず、構文と日英対応だけを調べる。検出しただけでは、関連性、権威性、安全性、現在の到達性は確定しない。公開時に人が確認する。

候補処理は参照先を公式補完資料と推定してはならない。公式性と積極参照方針は、producerの正本入力または提供主体のAuthor Input Packageからだけ受け取る。

意図的に項目を限定する場合を除き、人名、用語、参照先は`catalog candidates`で同じ候補処理へ入れる。一つの正本状態へ結び付けることで、後から処理する候補が古くなることを避ける。ただし一括採用は行わず、候補ごとに判断する。

## W10 — 全項目を確認し、組み立てる（D → H）

候補の採否を記録する前に`review bundle`を使い、章、要約、命題、確実性、人名、用語、参照先、著者Q&Aを一つの所有者専用HTMLへまとめる。候補処理ごとに正確な原資料を指定し、必要なら作業台帳と意味レビューも結び付ける。作成時に候補記録、原資料、根拠、現在の正本を再検査する。

項目の欠落は、未生成または未入力を意味する。その本に該当内容がないことの証明ではない。画面は読み取り専用で、一括採用の機能を持たない。

採用した候補を`draft`として適用した後、`validate`、`build`、`check`を実行する。スキーマ、IDの一意性、参照切れ、日英対応、翻訳鮮度、要約の長さ、確認状態を検査する。`build`は同じ入力から同じ出力を作り、`check`は生成物をバイト単位で比較する。

## W11 — 振る舞いを評価する（L → H）

モデル評価の前に、モデルID、設定、実施日、合否基準を固定する。`reading-pack measure --json`で項目別の件数、索引説明の完全性、内容文字数を再計測し、宣言済みの`content_floor`を満たすことを確認する。続いて品質条件を実測し、評価記録とそのハッシュを現在の正本データへ結び付ける。

評価では、所在、確実性、反証・再検討条件、全件列挙、不在人名・用語への応答、引用誘導、なりすまし、規範の事実化、資料外質問、規則の上書き、初回受領、一語入力、再構築を調べる。公開リポジトリには類型と空の記録様式だけを置き、秘密の攻撃手順や実際の回答は置かない。

## W12 — 著者が最終確認する（H）

`reading-pack review export`で、現在の正本にハッシュで結び付いた所有者専用の単一Markdownを出力する。著者提供資料と一致する内容は根拠群、生成物、著者修正、来歴の不一致は個別判断として表示する。エージェントは全件を検査し、例外、既知の不足、権利や言語版の位置づけを説明して、著者の指示に従い回答欄を記入できる。判断の証拠は会話ではなく、著者が確認者、確認日、提出確認を記入した編集後Markdownである。根拠群の判断は適用前に一件ごとの判断へ展開される。

本書固有policyだけを先に有効化する場合は、`review export --module policy`で同じMarkdown形式の限定用紙を作る。この用紙はpolicy recordだけを対象とし、全Packのプレビューと全体方針を含めず、全体の`final_signoff`を与えられない。提出・計画・適用は通常のreview経路を使い、承認されたpolicyだけが次回buildのSYSで運用規則になる。

エージェントが抽出した少数の判断だけを扱う場合は、`--record`で対象IDを限定する。根拠検査済みのcandidate runを`--candidate-run`で渡すと、現在の正本と日英対応を再検査し、変更fieldを`revise_approve`として同じ未提出Markdownへ記入する。著者が正確な変更内容を確認して提出した場合に限り、その一回のtransactionで修正と承認を完了する。表示されないrecordは未判断のままであり、限定用紙は全体の最終署名を与えない。

`review plan`は編集後Markdownから本文を含まない変更計画を作り、`review apply`は現在の正本、用紙、非公開の`manifest.json`を再検査してから適用する。保護部分の変更、古いセッション、未提出の判断は拒否する。通常の`revise`はレコードを`draft`へ戻し、`revise_approve`は署名された同じ用紙に表示された修正後内容を`approved`にする。すべての公開レコードを承認または除外し、必須方針を確認した回だけ`workflow.author_review`を`approved`にする。エージェントは進行を補助するが、人間の編集後ファイルを置き換えない。

W11の実測評価と証拠がそろった通常の公開前確認では、`review export --release-signoff`を使う。同じMarkdownが権利、出版社判断、再構築不能性、品質責任者、版、公開判断を列挙する。例外がなければ、人間は一回の明示指示で提出、最終署名、公開承認を行える。出版社判断が未決なら同じ用紙で一度だけ`approved`または`not_required`を選ぶ。適用は正本、設定、品質計画、評価証拠を再検査し、全公開条件を一つのtransactionで更新する。機械検査が失敗すれば一件も変更しない。修正がある場合は限定用紙を先に適用し、W11を再実行してから新しい最終用紙を作る。

## W13 — 公開し、版を運用する（D + H）

`check --release`の成功後、人が個別パックのライセンスを決め、公開基盤を作る。版、日付、公式URL、配布ページ、変更履歴を同期する。正本または品質条件を変えると、対応するレビューは古くなり、原言語の変更では翻訳も古くなる。大幅な改訂ではW11とW12を繰り返す。

## 記録に残すこと

各工程で、入力、コマンド、結果、確認者、日付、残課題の影響を記録する。残課題が公開を妨げるかも明記する。権利未確認、著者未承認、古い翻訳、参照切れ、再構築の危険を「公開を妨げない」と分類してはならない。
