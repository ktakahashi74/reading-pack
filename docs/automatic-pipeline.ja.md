# 自動制作パイプライン

新規の生成・評価納品には[Pack生成と品質評価の納品](pipeline-delivery.ja.md)を使う。品質評点による自動採否を行わず、生成物と評価をユーザーへ渡す。このページの旧契約による合否・承認処理とは区別する。

`artifact-acceptance-1`は、内容・指示・ローカル配布物の直接検査、固定資源枠、一括修正最大1回、既存候補の別再判定、候補hashに結び付いた著者確認票までを実行する。標準の設問生成・回答・採点は0回である。無指定は`legacy-reader-evaluation-1`を維持する。 [直接検査による制作](pipeline-artifact-workflow.ja.md)。[モデル比較試験](pipeline-model-comparison.ja.md)は任意の開発・運用試験であり、個別Packの合格条件ではない。

以下の設問・保留試験を用いる自動制作の説明は従来契約を対象とする。個別の制作・レビューコマンドも引き続き利用できる。

このガイドは`legacy-reader-evaluation-1`の説明である。直接検査の新契約は[制作ガイド](pipeline-artifact-workflow.ja.md)を参照する。新契約の合否は回答成功や制作実績の証明書を必要としない。

新規runでは、設問・回答の生成前に読解支援の合格範囲を固定する。生成された設問の細部を、Packの必須採録事項へ自動変換しない。中心的な意味、重要な条件、正しい帰属は必須とし、付随的な数値は、情報の限界を明示してPack内にある適切で具体的な所在を案内する対応も認める。一般的な丸投げや、書かれた内容の誤りは認めない。既存試験の再開では元の範囲と結果を保持し、基準を変える場合は別の再評価として識別する。これは候補全体の再生成を要求するものではない。

自動ワークフローは実測適格性のないalphaである。従来契約のproductionモードには、工程全体の時間・費用枠と実測済みのワークフロー証明を必要とする。従来の研究用コマンドは明示的な`--experimental`を必要とする。制御試験の成功は実書籍の完成実績ではない。計画、実測、現在の限界は[時間・費用・品質の予測可能性](predictable-production.ja.md)にまとめる。

`reading-pack pipeline`は、本文から著者レビュー用の確認票までを固定手順で実行する。著者の追加資料は任意である。手順、合否基準、停止条件はプログラムが管理し、設定済みのAIは限定されたJSONの生成・判定を担当する。生成、採点、修正、再試験を、人が毎回指示する必要はない。

通常の人間判断は最後の著者承認に集約する。権利、出版社確認、公開判断も、その確認票に含める。機械評価の合格は著者承認ではない。今回の実装は承認済み成果物をローカルで生成するところまでであり、外部サービスへのアップロードや配備は行わない。

## 一度設定し、その後は本を入力する

制作環境に、JSON入出力を実装する三つのローカル実行ファイルを設定する。役割は生成、判定、読者回答である。各実行ファイルは指定モデルを使用し、実際のモデル名を返し、送信先の出力・トークン設定を守る必要がある。役割ごとに独立したリクエストと文脈を使う。同じ基盤モデルを使う構成も可能である。Claude CLIを使う任意の接続アダプターも同梱する。CLI本体、利用モデル、認証、送信・費用の上限は制作環境で明示設定する。

```sh
reading-pack pipeline recipe --experimental --output recipe.json \
  --generator /path/to/generator --generator-model generator-model-id \
  --judge /path/to/judge --judge-model judge-model-id \
  --reader /path/to/reader --reader-model reader-model-id

reading-pack pipeline start --experimental book.md --run private/book-run --recipe recipe.json

# 著者の追加資料がある場合
reading-pack pipeline start --experimental book.md --run private/book-with-extras --recipe recipe.json \
  --supplement author-canon canon.json --supplement author-data appendix.md

reading-pack pipeline status --run private/book-run
reading-pack pipeline resume --experimental --run private/book-run
```

`--prepare-only`は入力固定までを実行し、AIを呼び出さない。`--title`、`--author`、`--format`は任意である。指定がなければ題名はファイル名、著者欄は`Unspecified`とし、著者を推測して確定しない。言語の自動選択は仮名を検出した場合に日本語、それ以外は英語となる。この推定が不適切な資料では設定の`language`を明示する。

追加資料の役割には`author-canon`、`author-data`、`author-qa`、`errata`、`bibliography`、`publisher-metadata`、`translation`を使える。資料の役割とハッシュを保持し、追加資料があるだけで本文を上書きする権威や、著者採択済みの状態を与えない。

既存の正準データを利用する場合は`--project existing-pack`を指定する。Author Input Packageから既に取り込んだ資料も、既存の記録と出典登録ごと隔離コピーへ継承する。最初の評価では変更のない文章と元の承認履歴を保持し、自動修正した内容は未承認の下書きに戻す。本文は既存プロジェクトの出典ハッシュと一致する必要がある。二言語の入力プロジェクトは主言語だけの制作対象へ投影する。他言語の原本は入力スナップショットに保持し、この実行からは配布しない。日英を協調して生成・翻訳する処理は未実装である。

既定の品質プロファイルは`auto`であり、試験前に本文の一部から七つの内蔵プロファイルの一つを選ぶ。既存プロジェクトを入力した場合は、そのプロファイルを継承する。設定で特定のプロファイルを固定することもできる。既定上限は候補4回、改善なし2回、AI呼出し1,000回、各処理の実行試行2回、各質問への回答2回、Pack全体10万文字・UTF-8で60万バイトである。要求項目は全件充足、重大誤りは0件を必要とする。利用条件の既定候補は`All rights reserved`であり、これも著者承認の対象となる。実行中に設定を変える場合は新しい実行を作る。

## 固定した工程と終了条件

1. 本文、追加資料、出典の役割、既存データ、設定、実装の版を固定する。対応形式の本文をローカルで正規化し、境界に重なりを持たせて分割する。原ファイルのバイト列が根拠となる。
2. 外部AIの呼出し前に、章構造を取得できるか、既存データと本文の出典が一致するかをローカル検査する。縦書きPDFで通常の抽出が失敗した場合は、文字位置と大きさから本文の章扉と節見出し候補を復元する。プロファイル選択後、候補の選別と独立検証を実行し、本文の見出しを確定する。目次の改題・欠落・追加との差は記録し、目次の件数に合わせて本文を削らない。検証不合格は固定回数だけ修正し、未達なら問題生成の前に停止する。その後、各入力範囲から改善用と最終試験用の問題を作る。問題の制約をSchemaと共通の設定から指示へ組み立てる。原文区間IDから引用を取得し、出典と位置を確定してから、別の判定処理が含意・条件・重複を検証する。不合格なら原案と指摘を渡して修正・再検証する。各区間で`max_rounds`回を上限とし、未達なら`failed_quality`で終了する。全区間の合格後に問題を固定し、回答を見て問題や要件を変更しない。
3. 候補を生成し、既存の候補検証処理でSchemaと出典を検査する。独立したAI判定を通った候補だけを、隔離プロジェクトへ`draft`として適用する。
4. 構造、必要な内容、文字数・バイト数、原資料に基づく章節数を検査する。出典への忠実さを監査し、固定問題への実回答を採点する。採点は全要求項目を扱い、実在する回答文と出典を根拠にする。判定保留は一度だけ別処理で裁定し、なお不明なら不合格とする。
5. 失敗を分類し、出典に基づく限定修正を作る。既存記録の置換は失敗箇所として指定されたIDに限定する。質問・反復ごとの点数が悪化した候補や、重大誤りが増えた候補は、最良候補を置き換えない。失敗を含む全候補を保存し、試行数・改善停滞の上限で止める。
6. 改善用の条件を満たした時点で、未使用の最終問題を一度試す。最終問題の回答を修正処理へ渡さない。不合格なら終了し、同じ最終問題への修正と受験を繰り返さない。
7. 著者確認票と私的な試験用プレビューを生成する。未承認の応答方針も評価できるよう、試験時だけメモリ上の投影で有効化する。正準データの承認状態は変更しない。

終了状態は`awaiting_author_approval`、`failed_quality`、`budget_exhausted`、`blocked_execution`、`needs_author_input`、`blocked_source_evidence`を区別する。品質未達は正規の終了結果であり、基準を引き下げる指示ではない。合成資料で検証できるのは自動実行と制御の動作であり、任意の実書籍での合格やAI採点の無誤謬性ではない。

Pack全体の容量と配布形式の容量は別に管理する。設定の`public_base_url`を指定すると、著者承認の前後に、既存Web配布物のローカル生成とバイト照合も実行する。指定URLの末尾には本のslugを追加する。現行Web形式には必要な節があり、その節を根拠付きで作れない本は配布検査で未達となる。人名、用語、誤読対策を捏造して条件を満たさない。単体Markdownの経路ではURL設定を空にする。この検査は外部チャット製品での取得互換性の実測ではない。

## 縦書きPDFの構造復元

`pdf-vertical`の章抽出が失敗した場合、追加のローカルPopplerコマンド`pdftohtml`で文字の座標とフォントサイズを読む。本文より大きい章扉、縦組みの行間・字下げ、目次と本文の対応を手掛かりにする。本文の章題を保持し、節は本文の候補から選ぶ。候補IDの捏造・順序変更をコードで拒否し、別のAI呼出しが漏れと誤採用を検証する。画像OCRは含まない。文字層のないPDFや判別できない組版は、成功を装わず停止する。

`source-preflight.json`、`source-import-plan.json`、`source-layout.json`、`structure-reviews.json`に出典と検証結果を保存する。レイアウト資料には本文を含むため、非公開の実行ディレクトリに置く。物理PDFページ番号は紙面のページ番号として配布物へ転記しない。一般の`import-plan`は本文を含まない章構造を返し、独立検証前の節候補を自動採用しない。

候補一覧から見出し自体が欠けている場合、検証AIは本文の見出し、物理PDFページ、見出しを含む短い原文引用を返せる。制御側が該当ページの一意な位置へ照合して候補を追加し、同じ反復上限内で再選別と独立検証を行う。本文中に文字列が存在するだけでは見出しとして合格しない。欠落が解消しなければ、問題作成前に停止する。

復元は対応する組版に対するヒューリスティックであり、全PDFへの適用や品質合格を保証しない。AI選別・検証にも固定呼出し上限を適用する。章ごとの構造検証入力が上限を超える場合は、無断の切捨てをせず明示的に停止する。

生成用Schemaは候補の採用規則から組み立て、ID接頭辞、各欄の長さ、`draft`状態を一致させる。著者の既存IDは元レコードのハッシュを照合した修正で維持できるが、同じ接頭辞の新規IDを自由に増やす許可にはしない。不正なレコードや本文断片に属さない原文区間IDは候補単位で隔離し、原応答を保存したまま他の有効候補を独立検証へ進める。開発用と保留試験用の設問は、本文断片ごとに各1問をSchemaで固定する。章要約には候補採用側の500文字上限も適用され、設定の要約上限が大きくても500文字を超えられない。

## 必須情報の固定と原文による再判定

生成前に`audit-contract.json`へ、プロファイルの必須モジュールと各章の案内を、固定ID付きで保存する。検証済みの開発設問はhashで固定し、設問の細部を採録ノルマにしない。生成・修正・監査は同じ条件を使う。採録不足の判定には既存の要件IDを必須とし、修正の途中で採録数のノルマや新しい義務を追加しない。原文への忠実さ、帰属、重要な条件、整合性、実際の構造誤り、ネタバレ規則は、開発設問の対象外の記述にも適用する。保留設問の要件は生成・修正・出典の再判定へ渡さない。

短い章要約に、すべての段落や例の網羅を要求しない。脚注の引用だけを理由に人名記録を必須にせず、引用文献ごとの採録数も課さない。判定にはPack内の別項目にある限定条件を含め、著者提供資料の役割を保持する。任意の補足は`advisories`に保存し、読解試験の停止や修正を起こさない。読解回答の採点でも、任意の助言と、実際の要件違反・重大誤りを分ける。

出典監査の疑義は、帰属誤り・架空記録の集計指摘も含め、独立した`audit_adjudicate`の判定へ最大4件ずつ渡す。入力は正準Pack全体と、固定した原資料から指摘の根拠、正規化本文の位置、登録済みの`file#anchor`参照、記録のアンカーを使って取得した原文である。帰属の疑義では、人名・用語の明示された表記を固定本文から完全一致で検索し、周辺の原文も取得する。検索件数だけで意味内容の不在を判定しない。再判定で検証した根拠が最初の疑義の原文範囲と異なる場合、修正先は検証済み根拠に従う。出典の役割・ハッシュ・位置を維持する。複数件で取得上限を超える場合、送信前に判定対象を分割し、必要なら1件ずつにする。上限自体は引き上げない。1回の原文範囲はrecipeの`audit_context_characters`で固定し、既定32,000文字、最大64,000文字とする。アダプター入力全体の1 MiB上限も維持する。未登録URLや任意のローカルファイルは取得しない。

判定は`blocking`、`advisory`、`dismissed`、`unresolved`のいずれかとする。合格を妨げる指摘には、固定された基準、読者への具体的な影響、検証済み根拠、修正範囲が必要である。疑義の棄却にも、入力された原文の根拠を要求する。未知の原文IDや判定対象の欠落はエラーとする。取得上限などで必要な原文を省略した場合、助言・棄却という応答でも未解決として扱う。これは独立したAI判定であり、意味判断の正しさを保証するものではない。元の指摘、判定、助言、モデルによる章節数の推定は、各jobと`audit-report-N.json`に保存する。

章節数は、原資料に結び付いた抽出済み、または独立検証済みの見出し一覧から数える。章の種別・題名・ページ位置、節題・順序を正準データと照合する。章構造の照合で記録済みの表記対応は、旧チェックポイントでも保持する。モデルの数値上の推定だけでは、この一覧を上書きしない。原文に基づく具体的な見出しの欠落や誤りは、引き続き監査指摘として解決を必要とする。

上限付きの追加検索と実行可能な出典付き修正を行っても根拠が確定しない場合は`blocked_source_evidence`で停止し、`unresolved-source-evidence.json`へ保存する。推測に基づく修正呼出しは続けない。確定した不具合の解消に、保護中の著者記録そのものの変更が必要なら、`needs_author_input`で停止し、`author-input-conflicts.json`へ保存する。どちらも未達であり、著者承認や改訂権限を自動で作らない。関連する編集可能な項目への補足で解消できる場合は、通常の上限付き修正を使う。既に明示された記録別の改訂許可は維持する。

判定条件とworkerプロトコルが変わるため、明示的な新規runまたはチェックポイントからのrestartを必要とする。旧指摘を遡って分類し直さず、旧runを合格へ変更しない。固定済み設問、既存費用、原資料の保護、保留回答後のrestart禁止は維持する。

## 著者判断と成果物生成

確認票は`RUN/candidate/.reading-pack/reviews/pipeline-author.review.md`に置く。この票以外の候補ファイルは固定する。内容、方針、権利、出版社確認、最終署名、公開判断を一つの票で扱う。AIが自分の判断で承認欄を記入してはならない。

```sh
# 著者が編集した確認票を提出した後に実行
reading-pack pipeline finalize --run private/book-run
# 編集済みの別ファイルも指定可能
reading-pack pipeline finalize --run private/book-run --review signed-review.md
```

著者が内容修正を返すと、`RUN/revisions/`に新しい実行を作り、問題作成、生成、監査、実回答試験へ自動で戻る。合格後に改めて著者確認票を出す。旧署名、下書き、評価、出典は保持し、古い評価値を変更後の内容へ付け替えない。明示的に提出された修正ごとに、新しい設定上限の範囲で実行する。

内容変更がなく全体承認と公開判断が署名された場合は、別のプロジェクトに承認を適用する。既存の公開検査を通過してから`RUN/release/dist/`を生成し、`release_ready`となる。これは承認済みのローカル成果物であり、サイトへの配備済みを意味しない。再実行では成果物を検証して再利用する。機械検査の不合格を署名で免除することはできない。

## アダプター仕様と復帰

各実行ファイルは標準入力からJSONを一つ読み、標準出力へJSONを一つ返す。要求には`schema_version`、`stage`、`job`、`recipe_sha256`、`model`、固定`prompt`、限定`payload`、`response_schema`、`request_id`が含まれる。応答Schemaは、その工程の結果形式を含む。

```json
{"schema_version":1,"request_id":"<要求と同じハッシュ>","model":"<実際のモデルID>","result":{}}
```

`result`を渡されたSchemaに従って埋める。工程名は`profile`、`structure_select`、`structure_review`、`benchmark`、`benchmark_review`、`generate`、`review`、`audit`、`audit_adjudicate`、`answer`、`grade`、`repair`である。候補記録は既存の正準Schemaと根拠となる原文区間IDを用いる。読者回答にはPackと質問だけを渡す。生成・修正要求には最終問題、正解要件、最終回答を含めない。要求は既存アダプターの上限1MiB、応答は設定された出力上限で制限する。実行ファイルは信頼済みコードとして扱い、sandboxではない。その利用者の権限でファイルやネットワークへアクセスできる。文脈の分離は入出力仕様であり、悪意ある実行ファイルからの隔離ではない。

実行ディレクトリは`0700`とする。本文、問題、原回答、根拠、著者票に非公開資料が含まれ得るため、公開するのは承認済み配布物だけとする。shellを介さず既存の制限付き環境で起動し、任意の環境変数は引き継がない。認証情報はアダプター側の既存の安全な設定方法で扱う。

呼出し回数は送信前に永続記録へ予約する。原応答はSchema・モデル照合の前に保存し、完了済み応答を再送信しない。不正な応答も保存して停止し、取り直して合格させない。実行エラーは上限内で再試行する。中断により結果不明の呼出しは、`resume --retry-inflight`で明示的に再試行する必要があり、追加の一回を消費する。制御対象は回数、試行数、時間、入出力容量であり、通貨建ての費用や事業者の請求額は測定しない。

入力、ツールキット実装、設定した実行ファイルやスクリプトが変われば復帰を拒否する。アダプターの依存環境は、その運用側で固定する。出典コピー、保存済み応答、候補ファイルはハッシュで検査し、一つの実行器だけがロックを保持する。候補は一時領域に保存してからrenameする。チェックサムは通常の編集や破損を検出するが、悪意あるローカル利用者に対する署名認証ではない。保存済み結果からの再生と、確率的なモデルへの新しい生成依頼は区別する。

## 原文区間と設問修正の契約

通常の出典根拠は`evidence_spans`から`span_id`を選んで返す。各区間は最大500文字で、原ファイルのハッシュ、文書ID、抽出本文内の文字位置、原文を保持する。`source.text`は送信時に同じ本文の区間一覧へ置き換わり、本文を重複送信しない。一般の根拠欄は`source_id`と`span_id`、候補生成の根拠欄は`span_id`を返す。制御側が原文を取得するため、全角・半角、空白、句読点をAIが再入力する必要はない。PDF見出しの`evidence_quote`と採点時の`answer_quotes`は別の欄であり、引き続き原文との照合を行う。

各区間から開発用1問・最終試験用1問を作り、各問の要件は2〜4項目とする。要件数を指示とSchemaで別々に定義しない。`max_rounds`は、章ごとの構造修正、区間ごとの設問作成・修正、Pack候補の各反復上限として適用する。これらすべての呼出しは共通の`max_calls`にも算入する。設問の各原応答と判定はjobsと`benchmark-reviews.json`に保存する。Schema不適合、未知の区間ID、重複、意味の不合格を修正対象とするが、包絡形式やモデルIDの不一致は実行障害として停止する。

## 任意のClaude CLIアダプター

インストール後の`reading-pack-claude-adapter`、または`python -m reading_pack_producer.claude_adapter`をworkerの`command`へ設定できる。コマンド引数には`--cli`、`--cli-sha256`、`--model`、`--effort`、`--audit-dir`、`--max-calls`、`--budget-usd`を明示する。CLI実体への絶対パスとSHA256を固定し、認証はCLIの安全な既存設定を用いる。三役で一つの費用上限を共有する場合、同じ非公開監査ディレクトリを指定する。`--call-budget-usd`の既定は5、`--timeout-seconds`は550秒で、制御側のtimeoutはこれより長くする。

接続例の引数は次の形となる。モデルと費用は制作環境で決める。

```text
reading-pack-claude-adapter --cli /absolute/path/to/pinned/claude --cli-sha256 SHA256 --model EXACT_MODEL_ID --effort medium --audit-dir /absolute/private/run/cli-audit --max-calls 100 --budget-usd 40
```

返却専用の`StructuredOutput`だけを受け付け、操作ツールとサブエージェントを禁止する。CLIへ渡すSchemaでは未対応のDraft宣言を除き、`dependentRequired`を同値な`if`・`then`の必須欄制約へ変換し、全制約をアダプターと制御側で検査する。CLI内の出力修正は最大3出力とし、先行出力がSchema不適合で対応するエラー通知がある場合だけ許す。有効な判定の取り直しは拒否する。設問内容の修正はこの接続処理ではなく、前述の制御工程が行う。

原要求、原ストリーム、実モデル、費用、判定を非公開監査へ保存し、同一要求の有効応答は再送なしで再生する。失敗した応答も保存し、同じ要求を自動再送しない。結果不明の中断はその呼出しの上限額を予約済みとして扱い、上限を超える次の送信を止める。費用制限はCLIの申告費用と呼出し上限に基づくもので、請求額の保証ではない。アダプター設定変更には新しい監査ディレクトリと新しいpipeline実行が必要となる。
## 生成と再開

生成は評価用の本文断片とは別に、既定で最大12,000字、1応答最大24候補へ分割し、審査は8候補ずつ行う。 対象が決まった修正では、既定で評価用の本文区間をまとめて用い、`repair_chunk_characters`で別の上限を指定できる（最大50,000字）。候補数と審査の上限は生成時と同じである。Author Input Packageのモードを審査・適用前に強制し、内容の揃ったseedは先に評価して必要な箇所だけ修正する。候補レコードのSchemaは通信の応答形式と分離し、不正な1候補が正常な候補の受領を妨げないようにする。修正対象外の既存記録を置き換える提案も、その候補だけを隔離し、対象の記録を保持する。不採用の候補は監査記録に残す。合否は、不採用候補の件数ではなく、独立審査を経た完成候補Packの検査と読者評価で決める。

任意のrecipe欄`generation_chunk_characters`、`max_generation_candidates`、`review_batch_size`で上限を固定する。実装更新後は`pipeline start --reuse-preparation-from PREVIOUS_RUN`により、同一のプロファイル選択・章構造・設問作成の応答だけを引き継げる。入力、seed、言語、断片分割が一致し、個々のプロンプト・入力・モデル・応答Schemaも一致する場合に限る。変更された処理は新たに実行する。保留試験への回答が始まった履歴からは再利用できない。元の要求、費用、ジョブIDは前のrunに残し、再利用票に出所と過去の予約呼出し数を記録する。生成候補、読者回答、採点、著者承認は引き継がない。

生成目標は候補数上限の半分とし、少数の数え間違いで候補全体を失わないよう余裕を持たせる。省略された不変の章情報は正本の章レコードから補い、補完記録を残す。空欄のページ情報も対象である。値の変更は引き続き拒否する。監査には正本の内容を一度だけ渡し、同内容の表示版を重複送信しない。修正には現在の原文区間に根拠のある指摘と、未解決の全体検査だけを渡す。

`evaluation_batch_size`を2〜4に設定すると、採点でPack入力を共有できる（既定値1）。読者の回答は常に1問ごとの別の要求とし、入力はPackとその1問だけに限定する。別の設問・原文の根拠・他の回答は読者間で共有しない。採点側は複数の回答を受け取るが、各採点には当該問題に属する根拠IDだけを使える。IDの重複・欠落や別問題の根拠の流用は停止条件となる。開発用と保留試験用を混ぜず、繰返し回答も別の文脈で実行する。

採用候補を適用する前に参照先も確認する。提案された確実性レコードが不採用なら、それに依存する命題や読者向け注記も除外し、既存の有効な参照先は保持する。`pipeline restart --from-run OLD --run NEW --recipe recipe.json`は、制御処理や接続の中断後に、生成・独立審査を含む同一の保存済み応答を再利用して候補を組み立て直す。候補の元の作成情報を維持し、再開時刻は別に記録する。原文、著者入力、依存関係、プロジェクト全体の検査は現行処理で再実行する。プロンプト、Schema、モデル、入力が変わった応答は再利用しない。保留試験の回答が1件でも始まった後は再開による制作修正を拒否する。旧runと費用の履歴は残し、新しい接続設定には全体予算の残額を指定する。


## 本文の章節地図と未承認の改訂案

既存のMarkdown・Orgプロジェクトは、本文の入れ子見出しと巻末資料まで照合し、提供済みIDと文章を保って章節地図を補完する。過去に著者承認された記録の自動修正は、元の判断を保持したまま未承認の改訂案として記録する。出典・構造検査を通過してから読解試験を行う。修正処理には出典付きの開発用設問を渡し、保留試験の設問・回答は渡さない。

私的な`source-text-outline.json`に本文位置と明示的な見出し別名を、`seed-reconciled-import-plan.json`に補完後の取込計画を記録する。著者提供の章構造は保護し、本文との不一致を期待件数から消さず、出典監査へ示す。空の要約に対する修正指示は、該当する見出しが得られる場合、その本文領域へ結び付ける。

`author-review-state.json`の任意項目`draft_revisions`は、変更後の下書きを直近の著者確認済み内容ハッシュとAuthor Input Packageのモジュール状態へ結び付ける。著者判断の作成や内容の承認は行わない。記録のない変更、古い改訂元、承認状態だけの書換えは引き続き整合性検査で失敗する。改訂案の採用には、その内容に対する新しい著者判断が必要であり、過去の判断は変更しない。

生成・修正用の入力では、変更禁止の著者提供記録の文章を省き、ID・内容ハッシュと省略を示す説明を保持する。正準データは変わらない。独立した出典監査、読者への入力、採点、著者確認ではPackの全内容を保持する。修正への設問情報は開発用だけを使う。出典検査を通過するまで読解試験は延期し、得点なし・未合格として記録する。延期した試験や出典検査の不合格を、合格の根拠にはしない。

Claudeアダプターは元の要求バイトと実際のCLI入力を別々に保存する。CLI入力では共通のPackを、質問・処理IDなど毎回変わる情報より前に配置する。JSONの全内容とSchema制約は保持する。読者呼出し間で共通する入力先頭部を確保するが、実際のキャッシュ利用や費用削減は原監査記録で測定し、効果を前提にしない。


## 修正範囲

集計用の出典エラーだけでは無関係な本文断片の修正を起動しない。個別のエラー情報と出典範囲を保持し、著者提供記録に関する補足は関連する編集可能な章要約・用語などにも提案できる。提供済み記録の保護と合格条件は維持する。

監査の帰属誤り・架空記録一覧は、元の詳細と本文区間を修正指示へ保持する。本文区間は修正対象を選ぶための情報であり、引用根拠として扱わない。集計上の疑義も原文による独立の再判定を行い、確認された違反は合格を妨げるが、それだけで全断片に生成を要求しない。変更禁止の著者提供記録に指摘がある場合は、その記録だけを読み取り専用の文脈として渡し、章・命題の対応から関連する編集可能なIDを追加する。候補の審査・適用時には、記録と個別フィールドの保護を引き続き強制する。矛盾が解消しなければ合格しない。

### 実装更新時に停止した下書きを保持する

通常の`pipeline restart`は、元のseedと完全一致する保存応答から候補を組み立て直す。生成済みの記録をそのまま保持する場合は、次のどちらかを明示する。

```sh
reading-pack pipeline restart --experimental --from-run OLD --run NEW --recipe recipe.json --checkpoint-round 0
# または、停止中の作業用下書きを保持する:
reading-pack pipeline restart --experimental --from-run OLD --run NEW --recipe recipe.json --working-checkpoint
```

`--checkpoint-round N`は、保存されたラウンドのファイル一覧と表示Packのハッシュを検証する。`--working-checkpoint`は、`blocked_execution`、`failed_quality`、`needs_author_input`、`blocked_source_evidence`で停止したrunだけを受け付け、未検証の作業用下書きと明記する。どちらもプロジェクトと出典の来歴を検査し、原入力と固定済みの設問を保持して、選択した内容のハッシュを記録する。明示的に保持した下書きでは初回生成を省略し、要約や必須項目の不足を検査して上限付きの修正へ渡す。過去の品質合格や著者承認を付け替えない。完全一致する応答だけを再利用でき、要求が変わった処理は新たに実行する。保留試験への回答開始後は引き続き再開を拒否する。チェックポイントのラウンド番号を保持し、完全一致する完了済み監査を再利用する。ラウンド上限はリセットしない。旧費用は使用済みとして残し、新しいアダプターには全体予算の残額を設定する。

章候補の審査では、ID、種別、章題、ページ、節のうち既存の章と完全一致する項目をコードで確認する。保持された値のすべてが今回の生成用原文区間に現れる必要はない。要約、用語、ネタバレ範囲を含むその他の新規・変更内容は、独立した原文照合を引き続き必要とする。新しい記述に根拠がなければ不採用とし、構造の変更値を不変と認定しない。完成した章節構造全体は、別の出典監査でも検査する。

### 著者提供記録の改訂案を明示的に許可する

著者提供記録は標準では変更禁止である。ユーザーが指定した記録の改訂案作成を明示的に許可した場合は、チェックポイントからの再開時に`--permit-draft-record ID`を必要な件数だけ指定し、`--authorization-file permission.txt`で実際の許可を記録したファイルを渡す。ファイルを作る操作自体を、ユーザーの許可の代わりにしてはならない。`--prepare-only`を付けると、モデル送信前に内容を確認できる。

再開処理は原記録とAuthor Input Packageの状態を保持し、許可のハッシュを記録して、指定IDの未承認改訂案だけを認める。`provided`モジュールへのID追加や、過去の著者判断の変更は行わない。候補の根拠確認と独立審査は引き続き必要である。改訂履歴は変更後の内容を元の内容とモジュールのハッシュへ結び付け、無記録変更、古い許可、承認状態の捏造を拒否する。著者が提供した来歴は保持し、新しい候補の原文所在とは分けて記録する。改訂内容の採択には新たな著者判断が必要であり、採択後の本文へ古い改訂許可を流用しない。

### ウェブリンクを含まない本文の参考文献

参考文献にはID、原文に基づく`label`、確認状態が必要であり、`url`は任意である。著者名、題名、刊行年など、原文で確認できる書誌情報だけをlabelに記録し、欠けた情報やウェブアドレスを補作しない。引用先の表示は、本書がその文献に言及したことを示すものであり、当該文献の本文を取得済みであるとは意味しない。候補の根拠確認と独立審査は引き続き必要になる。

URLを指定する場合は、絶対HTTP(S)アドレスとする。`official_companion`には引き続きURLと既存の範囲・取得方針の宣言が必要である。既存のURL付き参照の表示は変わらない。別機能のURL/DOI索引抽出はリンクを検出し、自動生成とAuthor Input Packageはリンクのない書誌情報にも対応する。

## 章候補を審査する原文の範囲

章の内容を変更する候補では、同じ固定原文の前後も審査へ渡す。`chapter_review_context_characters`で拡張範囲を固定する（既定120,000文字、最大150,000文字）。元の区間が既にその上限より長ければ、切り詰めずに元の範囲を保つ。送信前に出典hash、連続性、原文位置を検査する。これにより生成・修正の分割境界をまたぐ章を照合できるが、任意の長さの章全体を含む保証ではない。新しい記述の独立した根拠確認は引き続き必要である。この前後拡張は同じ文書内に限る。参照先の原文区間は以下の手順で別途取得する。読解試験には引き続きPackだけを渡す。

新規の設問は、短い読解支援Packに必要な情報かを審査してから要件を固定する。再開時は固定済み設問を変更しない。監査で未確定の指摘には、各ラウンドで一度、上限付きの原文検索と再判定を行う。確認済みの出典に限定した表現へ修正できる場合は、確定不具合の修正とともに独立審査・再監査へ進める。未確定のまま合格にはせず、既存のラウンド・予算上限を維持する。重複する指摘は理由と根拠を失わず統合する。

`audit_lookup`は登録済み原文IDに対する完全一致の検索語を最大6件選ぶ。取得する原文には既存の監査文脈上限を適用し、任意のファイルやURLは取得しない。出典を限定する修正でも、独立審査と全体監査で決着するまでは疑義を未確定のまま保持する。検索と再判定は`resolution_attempts`に保存し、統合した指摘も元の観測をすべて保持する。これらの処理は保護された記録の改訂権限や著者承認を作らない。


候補審査にも、候補・対象記録の出典所在と元の指摘から取得した原文を渡す。明示的な訂正の確認に必要な本文・付録を、役割と正確な原文区間を保って照合し、Pack内の参照先記録も文脈として添える。取得には既存の監査文脈上限を適用し、無関係なファイルや読解試験の設問は含めない。引用できるのは渡した区間だけであり、根拠が未確定なら採用しない。

採点者の回答引用が対応する `**` 強調記号だけを省いた場合は、回答内の実際の文字列を復元し、双方の表記と位置を記録する。文言、句読点、空白、数値、条件の一致は引き続き必須とする。点数を変えたり、回答要件の欠落を許したりする処理ではない。それ以外の引用不一致は実行エラーとして止める。


採録不足の修正先は、同じ原文区間にある別の指摘とは独立に選ぶ。固定要件の不足理由で明示された既存IDは、著者契約上の改訂許可があれば候補に含める。他の指摘に対象IDがあるために、この追加先を落とすことはない。追加先が明示されない場合は既存の補完処理により編集可能な記録を提示し、保護された記録は除外する。前のラウンドで候補を差し戻した理由も次の修正へ渡すが、新しい合格条件や追加ラウンドは作らない。完了済みチェックポイントからの再開でも、報告書のハッシュに拘束して差戻し理由を保持し、連続引用量で拒否した候補を理由なしに再提案させない。

再判定者には、`development:<case>:<index>`が固定設問の要件IDであり、Packのモジュールや記録ではないと明示する。Pack内の正本記録は全体を渡しており、その中で要件の意味が満たされるかを確認する。固定要件そのものを変更する説明ではない。

既知の確定不具合や未確定事項は、次の全体監査が再掲しないだけでは消さない。同じ記録の問題または固定要件について今回の監査に明示的な判断がなければ、現行Pack全体と固定原文による焦点を絞った再判定を行い、`known_findings_rechecked`へ残す。チェックポイントからの再開にも元の報告書ハッシュと既知の指摘を引き継ぐ。既存の呼出し・文脈・ラウンド上限を使い、この処理自体で合格を付与することはない。

候補審査の取得原文が既存の文脈上限を超える場合は、送信前に審査を分割し、必要なら1候補ずつ渡す。別候補の根拠が予算を使い、当該候補の本文根拠が欠ける事態を防ぐ。上限自体は増やさない。1候補でも足りない文脈は明示したままにし、確認済みとは扱わない。

採録不足の修正先を選ぶ際は、再判定が引用した原文に加えて、明示された固定開発要件の元の根拠も保持する。不足を確認した本文と、不足情報を記した遠い注や付録が別区間でも、必要な区間へ修正を送る。根拠は固定済み開発設問から取得し、指摘の文章から要件を推測したり、保留設問を参照したりしない。候補の原文照合・独立審査・全体評価は引き続き必要であり、修正回数と予算の上限も維持する。
