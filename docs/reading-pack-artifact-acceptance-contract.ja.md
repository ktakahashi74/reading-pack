# Reading Pack直接検査の状態・保存契約

状態: M1の状態・保存契約を維持し、M6〜M10で[制作・修正・再判定・著者確認](pipeline-artifact-workflow.ja.md)まで接続した。契約IDは`artifact-acceptance-1`。

上位方針は[直接検査による合否判定案](reading-pack-artifact-acceptance-design.ja.md)。この文書は、合否、実行状態、任意のモデル診断、著者承認を保存する境界を定める。Packの収録内容形式、既存の長さ・引用上限、予算、著者の権限は変更しない。

## 1. 正本と適用範囲

- 意味・優先順位・参照整合の正本: この文書。
- フィールド、列挙値、局所的な状態制約: [report.schema.json](contracts/artifact-acceptance-1/report.schema.json)。
- 保存例: [examples.json](contracts/artifact-acceptance-1/examples.json)。すべて合成例であり、実書籍の結果ではない。
- 契約検証: `tests/test_artifact_acceptance_contract.py`。

M1で固定したSchemaは`docs/contracts/`に保持する。現在は同一バイトの`schema/artifact-acceptance-report.schema.json`を実行時検証へ登録している。Schemaだけでは、参照ファイルの実在、原典忠実性、検査範囲の十分性、承認の真正性を検証できない。

新契約を選ぶ識別子は`contract_version = "artifact-acceptance-1"`とする。無指定の旧runを新契約として解釈しない。新契約の意味を変える場合は新しい契約IDを使い、既存記録をそのまま保持する。フィールドの追加・変更にも互換性判断を要する。実際に新runで選択・固定する処理はM2で実装した。

## 2. 四つの状態

| フィールド | 値 | 意味 |
|---|---|---|
| `acceptance.status` | `pass / fail / inconclusive / not_run` | 固定された直接検査の結果 |
| `execution.status` | `ready / running / completed / stopped` | 自動工程がどこまで動いたか |
| `model_diagnostics.status` | `not_run / incomplete / completed` | 任意の利用モデル試験の実施状態 |
| `author_approval.status` | `not_requested / pending / needs_decision / approved / rejected / changes_requested` | 現候補についての著者確認・判断の状態 |

単一の総合statusへ潰さない。たとえば欠陥が残り、途中で期限切れになった場合は、`acceptance.status = fail`、`acceptance.coverage = incomplete`、`execution.status = stopped`、`stop_reasons = ["deadline_exceeded"]`を同時に保存する。

`completed`は予定した自動工程を終了した意味であり、品質合格、モデル全問正答、著者承認を意味しない。固定の修正1回で欠陥が残った場合も、予定の検査・報告まで終えたなら`completed + fail`となる。固定枠の追加参照を終えても疑義が解消しなければ、`completed + inconclusive`となる。

## 3. 合否の優先順位

以下の順序で一意に決める。モデルの回答スコア、著者の賛否、実行停止理由を入力にしない。

1. 現候補に結び付く確認済み欠陥が1件以上ある: **fail**。未検査範囲や未解決疑義も併記する。
2. 直接検査がまだ始まっていない: **not_run**。確認済み欠陥・疑義の配列は空、検査報告はnullとする。
3. 必須検査が未完了、または具体的疑義が未解決: **inconclusive**。
4. 必須検査がすべて完了し、確認済み欠陥も未解決疑義もない: **pass**。

| coverage | 確認済み欠陥 | 未解決疑義 | status |
|---|---:|---:|---|
| `not_run` | 0 | 0 | `not_run` |
| `incomplete` | 1以上 | 任意 | `fail` |
| `complete` | 1以上 | 任意 | `fail` |
| `incomplete` | 0 | 任意 | `inconclusive` |
| `complete` | 0 | 1以上 | `inconclusive` |
| `complete` | 0 | 0 | `pass` |

`coverage = complete`は、検査対象と必要な原典範囲を固定した一覧に対し、必要な検査を終えた状態である。モデルの返却が成功しただけでは成立しない。検査を実行したが意味の判断が未解決という状態は、`complete`と未解決疑義の併存で表せる。必要な資料を渡せず検査自体を完了できなければ`incomplete`とする。対象一覧が未確定、空、または項目が漏れている状態を`complete`にしない。

検査開始後の空の指摘一覧は合格の根拠にならない。検査対象一覧、完了範囲、証拠の整合が別途必要となる。

## 4. 保存する情報と参照の単位

保存先はrun内の`acceptance/records/<record_id>.json`とする。記録は追記式で、既存レコードを書き換えない。各`record_id`はrun内で一意とし、保存処理ではパスとして直接解釈せず安全性を検査する。

参照は`{ "path": "runからの相対パス", "sha256": "ファイルバイト列のSHA-256" }`に統一する。絶対パス、URL、親ディレクトリへの脱出を認めない。symlinkの解決後もrun内である必要がある。相対パスの起点はレコードの置かれたディレクトリではなくrunルートである。共有・旧run資料は不変の証拠束としてrun内へ保持し、その索引から元の識別子を追えるようにする。巨大な原資料の複製方法や保管方式はM8で決めるが、参照先の同一性と旧資料の不変性を要件とする。

| フィールド | 必須の内容 |
|---|---|
| `record_id`, `created_at` | 記録ID、タイムゾーン付き作成日時 |
| `previous_record` | 同じ評価系列の直前レコードへの参照。初回はnull |
| `reassessment_of` | 旧方式から別契約で再判定する場合の元run manifestへの参照。新規制作はnull |
| `bindings.run_manifest` | run識別子、契約ID、エンジンhash、モデル・設定、recipeの固定情報 |
| `bindings.candidate_manifest` | 判定対象の全正本ファイルのhash一覧。候補未作成ならnull |
| `bindings.source_manifest` | 全原資料のhash、資料ID、役割・優先関係、抽出物と元資料の対応 |
| `bindings.instruction_template` | 共通指示テンプレート版・内容・検査根拠 |
| `bindings.acceptance_criteria` | 固定の基準ID、採用プロファイル、長さ・引用・配布の制約 |
| `bindings.delivery_manifest` | 実際の配布物全件のhash、選択した配布経路、候補との対応。未生成ならnull |
| `acceptance.report` | 下記の直接検査報告への参照。未実施ならnull |
| `resources` | 累計予算の識別子と台帳への参照 |

意味検査の開始後はcandidate manifestを必要とし、passにはdelivery manifestも必要とする。候補のファイルが変われば新しいmanifest・レコードを作る。同じ旧hashのまま判定や承認を流用しない。

直接検査報告には、次を含める。内部Schemaと実行処理はM4〜M6で実装した。これらの情報を落とさないことはM1で固定する。

- 対象候補、原資料、基準、テンプレート、配布物への結び付き。
- 全収録項目、共通指示と書籍固有差分、章の主要論点、全体整合、選択した配布機能を含む固定対象一覧。
- 必須検査のID、対象と原典範囲、実施状態、方法、モデル・設定、証拠への参照。対象一覧と完了一覧の対応。
- 確認済み欠陥、具体的な未解決疑義、助言・棄却した指摘の区別。欠陥・疑義のIDはレコードの配列と一致させ、両分類に重複登録しない。
- 欠陥の対象位置または固定要件ID、違反基準、原典・構造検査の証拠、読解への影響。欠落項目には存在しない項目IDを作らず要件IDを使う。
- 修正前後のhashと差分、変更の影響範囲、再検査範囲。初回の合格や未実施では修正なしと明記する。

配布物の機械検査は直接検査に含める。明示的に約束した取得機能も固定対象に含め、その結果を独立した欄で表示する。非採用の配布経路、任意のモデル回答試験、制作方式の実績測定は必須検査一覧へ自動追加しない。

## 5. 停止理由と資源

`stop_reasons`は`stopped`のときだけ1件以上、それ以外では空とする。複数の観測事実があれば併記し、品質と実行停止のどちらかを隠さない。

| code | 意味 |
|---|---|
| `deadline_exceeded` | 工程の期限を超えた |
| `budget_exhausted` | 累計の呼出し・費用枠の残量不足 |
| `phase_budget_exhausted` | 工程別の呼出し・予約枠の残量不足 |
| `cost_unknown` | 必要な使用・費用記録を確定できない |
| `cost_allowance_exceeded` | 記録された費用が固定枠を超えた |
| `input_constraint` | 入力・資料構造・サイズ等が固定条件を満たさない |
| `provider_error` | providerまたは通信の障害 |
| `invalid_response` | 応答形式・必須情報が契約を満たさない |
| `interrupted` | ユーザー停止、プロセス中断等 |
| `integrity_error` | hash、参照、固定契約等の整合が破れた |
| `superseded` | 明示的な後継runへの引継ぎにより停止した |

詳しい発生工程、理由、未完了作業はrunの実行記録へ保存する。欠陥や未解決疑義そのものは停止理由へ移さない。修正枠を使い切った結果も、検査報告と資源台帳で表す。

予算台帳は元の累計枠、既使用量、予約、今回の使用量、元の期限、後継への引継ぎを保持する。既存runの再開では元の期限を維持する。別の再判定計画には新しい明示的な実行条件を固定するが、累計枠を初期化したり、旧期限を上書きしたりしない。CLI報告額、予約額、実際の請求額を区別し、費用不明を0としない。M1では追加予算や新しい時間上限を設定しない。

停止前に保存・検証された完了済みの直接検査は、対象hashが不変なら保持する。したがって報告工程の中断とpassは併存できる。ただしhash不整合でその証拠を信用できなくなった場合は、最後の有効なレコードを履歴として保持し、現状態をpassとして表示しない。新たな確認で欠陥がなければinconclusive、確認済み欠陥があればfailとする。

## 6. モデル診断と著者承認

モデル診断のcompletedは試験が終わった意味である。報告には、モデル・設定、対象Pack hash、取得方法、試験計画、実施数・未完了数、回答結果、原因の判別状況、費用を保存する。誤答だけで直接検査の欠陥を作らない。Pack欠陥を確認できた場合は、その証拠を持つ新しい直接検査レコードへ反映する。旧契約の回答結果を新契約の直接検査へ転記しない。

著者欄は次の意味とする。

| status | 意味 |
|---|---|
| `not_requested` | この候補について著者確認をまだ開始していない |
| `pending` | passの候補について、確認票を用意し著者の採否を待つ |
| `needs_decision` | failまたはinconclusiveの候補について、著者判断を要する内容と根拠を確認票へ集約した |
| `approved` | 記録された候補に対する明示的な著者承認の証拠がある |
| `rejected` | 著者が候補を不採択とした証拠がある |
| `changes_requested` | 著者が変更を求めた証拠がある |

`pending`と`needs_decision`には確認票、実際の判断には確認票と判断記録を必要とする。`needs_decision`には具体的な質問IDも必要とする。いずれもcandidate manifestのhashを固定し、レコードの候補と一致させる。判断記録は判断者、日時、対象hash、判断内容、承認範囲を含む。著者の固定内容は確認待ちの間に変更しない。

著者承認は品質合格の代用にならない。同一候補について承認後に欠陥が見つかった場合は、承認証拠を残したまま`approved + fail`を記録できる。候補が変わった場合は旧承認を履歴に残し、新候補へ自動継承しない。著者の変更要求を品質不合格へ変換しない。公開・送信の権限は別途必要であり、この契約には自動公開状態を設けない。

## 7. 更新と移行の規則

1. 記録の各参照先を先に保存し、hashと内部整合を検証してからレコードを原子的に保存する。途中ファイルを完了証拠にしない。
2. 通常の推移はreadyからrunning、その後completedまたはstoppedとなる。明示的な再開は同じ資源枠で新レコードを作る。停止理由は旧レコードに残す。
3. 修正後は新候補へ結び直し、必要な再検査が終わるまでpassにしない。未変更部分の証拠は、候補差分・依存関係・基準・原資料の一致を確認した範囲で再利用する。古い欠陥は修正履歴に残し、新候補の確認済み欠陥へ無条件にコピーしない。
4. 旧方式からの再判定は別run、初期statusはnot_runとする。旧runの状態、判定、候補、固定設問、承認、累計費用を保持する。契約変更だけで合格へ塗り替えない。
5. 新しい指摘や承認は追記レコードで反映する。過去の合格記録を書き換えず、表示する現状態を更新する。

実行時に必要なSchema外の検証は、日時の暦上の妥当性、参照先の存在とhash、manifest内の全ファイル、契約・候補・原資料・配布物・承認の対応、検査対象一覧の十分性と完了範囲、指摘IDの対応、資源累計と期限である。これらを省略してSchema適合だけでpassとしてはならない。

## 8. M1の完了条件と次の単位

M1の完了条件は、四状態の意味、合否の優先順位、停止理由、保存フィールド、証拠の結び付き、更新・旧run保持規則を上記のとおり固定し、保存例と不正な組合せをSchemaで検査できることである。

保存例は17件。未実施、開始前のprovider障害、実行中の未完了、合格、欠陥、欠陥と検査未完了の併存、疑義、予算停止、合格後の報告中断、モデル誤答とPack合格、モデル正答とPack不合格、承認待ち、承認、変更要求、承認後の欠陥、保護内容の判断待ち、旧候補の別再判定を含む。hashはすべて説明用の合成値であり、実在する検査証拠や承認ではない。

検証コマンド:

```sh
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python3 -m unittest discover -s tests -p test_artifact_acceptance_contract.py -v
```
