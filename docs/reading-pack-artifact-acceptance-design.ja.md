# Reading Packの直接検査による合否判定案

状態: 設計の実装はM10まで接続・検証した。現在の動作、固定プロファイルと全体再検査の制約、著者判断・公開の境界は[制作ガイド](pipeline-artifact-workflow.ja.md)を参照する。以下は設計の根拠であり、実書籍の合格や制作実績の記録ではない。

## 1. 目的と変更点

Reading Packは、読者が本の主張を理解し、必要な箇所へ戻るための読解支援資料である。制作の合否は、Packの指示、収録内容、参照先がこの用途を満たすかで決める。利用モデルの全問正答を合格条件にしない。

本文を入力し、著者が用意した付録や追加データがあれば併用する。その後は、事前に固定した工程と資源上限の中で、検査、必要な修正、再検査、著者確認票の作成まで自動実行する。著者の判断を要する事項は最終確認票へ集約する。

指示の正しさだけでは、誤った収録内容を救えない。また、直接検査にも見落としはあり、絶対無誤りを証明できるわけではない。「検査した範囲で必要な要件を満たした」と「どのモデルでも正答する」を明確に分ける。

| 対象 | 現行実装 | 提案 |
|---|---|---|
| 共通の応答指示 | 各冊の回答試験を通して繰り返し評価する | テンプレート改訂時に直接検査し、各冊では採用版と差分を確認する |
| 各冊の品質 | 原文監査に加え、developmentとholdoutの回答成功を必須にする | 配布されるPack自体の直接検査を合否の根拠にする |
| 利用モデルの誤答 | 正答率不足を`missing_coverage`として修正へ送る | 診断結果として保存し、Pack側の具体的な欠陥が確認された場合だけ修正へ送る |
| 設問生成・審査・採点 | 標準制作の必須工程 | 標準制作から外し、開発時の任意の利用試験へ移す |
| 終了条件 | 回答試験を通るまで、上限内で修正する | 直接検査と最大1回の修正・再検査で終える |

## 2. 合否の対象

### 共通指示

共通指示は検査済みのテンプレートとして版を固定する。各冊で全文を自由生成し直さず、資料名、資料の役割、具体的な参照先などを差し込む。既存の著者指示や書籍固有の指示がある場合は、その差分と共通指示との整合を検査する。

検査するのは、次の行動が明確で、互いに矛盾せず、宣言した利用環境で実行可能かである。

- 本の主張、著者の補足、外部情報、モデル自身の推測を区別する。
- 重要な条件、確実性、事実と規範の区別を保つ。
- Packで答えられる範囲と、原典へ戻る必要がある範囲を区別する。
- 未取得の資料を読んだと述べず、見つからないだけで原典に存在しないと断言しない。
- 詳細を収録しない場合、Packにある具体的で適切な所在を案内する。
- ファイル利用、Web取得などの利用形態に応じた取得手順と、取得できない場合の対応を示す。

各冊の検査では、テンプレートのハッシュ一致だけで終えない。実際に配布される指示が欠落・改変されていないか、差込み後の参照先や書籍固有の指示が矛盾していないかを確認する。

### 各冊の内容と構造

| 検査項目 | 合格条件 | 不合格にしない例 |
|---|---|---|
| 章・節への案内 | 実在する構成と対応し、各章の主要な論点を理解して戻れる | 各段落、各事例の要約がない |
| 中心的な主張 | 原典に忠実で、意味を変える条件・例外・確実性を保つ | 全論点を同じ密度で採録していない |
| 収録した記述 | 数値、比較、帰属、引用を含め、原典で裏付けられる | 正確な付随情報を短くする、または省く |
| 資料の役割 | 本文、著者付録、追加データを区別し、対応する箇所で利用・案内する | 追加資料がそもそも提供されていない |
| 参照先 | 章・節・注・項目IDなどが実在し、記述と対応する | 本文にないページ番号を無理に作らない |
| 全体の整合 | 複数項目の関係と留保を含め、互いに矛盾しない | 同じ留保を全項目へ重複記載していない |
| 形式・配布物 | Schema、必須項目、参照解決、採用した配布プロファイルの制約を満たす | 非採用の配布経路での互換性が未測定 |

中心的な論点が抜けた薄いPackを、形式検査だけで合格にしない。章ごとの原典との対照で、要約と主張の選択が読解支援の目的を果たしているかを確認する。一方、生成した質問から新しい採録義務を増やさない。

全ての収録項目を検査対象の一覧へ登録する。検査範囲に含めたという記録は、全ての誤りを検出した証明ではない。根拠のない比較や誤った数値は、付随的な記述であっても修正対象とする。表現の好みや追加できる事例は助言に分ける。

長さの数値を、この合否変更に便乗して変えない。生成時の項目上限、引用上限、配布物の文字数・バイト数・取得単位は別の制約として維持し、実行計画に固定する。数値や人名を網羅させるためにPackを膨らませない。

## 3. 直接検査の方法

機械で確定できる検査と、意味の検査を分ける。

機械検査は、形式、ID、出典位置、引用照合、必須項目、構造、長さ、配布物と正本の対応を確認する。意味の検査は、生成とは別の検査呼出しで、原典との忠実性、重要条件、主張の選択、指示の整合を確認する。同一モデルを使う場合でも生成時の自己申告を検査の代用にしない。

意味の検査へは、Pack項目と対応する本文、必要な前後文脈、参照された注・付録を渡す。生成側が選んだ一文の引用だけで正しいと判断させない。章の案内は対応する章の原典と照合し、全体の整合は関連項目を併せて確認する。本文、注、追加資料との対応を生成時から保存し、同じ巨大なPackを無関係な原文区間へ繰り返し送る処理を減らす。

指摘は次の三種類に分ける。

| 分類 | 必要な根拠 | 処理 |
|---|---|---|
| 確認済み欠陥 | 対象項目・指示の位置、違反した固定基準、原典または構造検査の根拠、読解への影響 | 修正対象 |
| 要確認 | 対象と具体的な疑義はあるが、文脈や資料が不足して判断できない | 固定枠内で一度追加参照・判定し、解消しなければ検査未完了 |
| 助言・根拠不足の提案 | 好み、任意の追加情報、具体的な対象を示せない一般論 | 記録のみ。合否と修正回数を消費しない |

出典の抜粋一つに見当たらないことを捏造の証拠にしない。一方、根拠が不足した疑義を理由なく棄却して合格にしない。追加参照・判定の総呼出し枠を事前に決め、指摘が増えるたびに枠を追加しない。

不足の指摘では、対象項目が存在しない場合もある。その場合は固定済みの要件IDと検査した範囲を示す。「もっと詳しく」「この質問に答えられない」だけでは欠陥にしない。

## 4. 各冊の固定ワークフロー

```text
本文 + 任意の著者資料
  → 入力・資料役割・構造・実行枠の確定
  → Pack生成
  → 直接検査
  → 欠陥があれば一括修正を最大1回
  → 変更箇所と影響範囲の再検査 + 全体の機械検査
  → 合否報告と著者確認票
  → 著者承認
```

初回検査を完了し、指摘をまとめてから修正する。項目ごとに修正と再採点を繰り返さない。修正後に新たな問題が見つかっても、二度目の修正を自動開始しない。

初回で欠陥がなければ修正と意味の再検査を省く。修正した場合は、変更項目、参照している項目、共通指示への影響を再検査する。依存関係を確定できない変更では再検査範囲を全体に広げるが、その最悪時の枠も実行前に確保する。機械検査は最終配布物全体で行う。

本文だけの場合も、章構成と本文から生成・検査を進められる。著者資料があれば、提供された各資料を入力一覧に登録し、対応する案内・主張・参照へ使用する。資料ごとの役割と優先関係はプロファイルの既定値を使い、本文と追加資料の立場を勝手に統合しない。

著者が固定した内容に疑義がある場合は、変更せず、根拠付きで最終確認票へまとめる。通常の生成・検査・修正の途中で著者へ小刻みに質問しない。合格候補は承認待ちへ進み、内容判断が必要な候補は判断事項付きの確認票へ進む。後者を品質合格とは表示しない。

## 5. 利用モデル試験の位置付け

標準の各冊制作では、利用モデル試験は0回とする。設問生成、設問審査、回答、採点、holdout合格を必須にしない。

共通指示や配布方法を変更した際の開発診断として、モデル、質問数、反復数、費用を固定した試験を任意に実行する。たとえば1モデル・6問・1回という小規模な組合せを採れるが、これは設定例であり、利用者の品質要求や今回の追加支出承認ではない。

結果は、モデル名・設定、Pack版、取得方法とともに記録する。誤答は「利用上の失敗」として残す。原因を確認できなければ「原因未特定」とし、モデル能力のせいだと決め付けない。

- Packの明確な指示を無視した誤答では、Packの合否を変えない。
- Packの誤記、指示の矛盾、取得できない参照先などが確認された場合は、その欠陥を直接検査の指摘として扱う。
- 通信障害や一時的な取得失敗では、利用環境側の状態を分けて記録する。

任意試験を行う場合も、その費用と処理枠を先に決める。修正枠を使い切った後にPackの欠陥が確認されたら、欠陥ありとして終了する。診断を理由に修正ループを追加しない。合格報告後の発見も追記記録で現行状態へ反映し、過去の報告そのものは書き換えない。

特定サービスでの一回操作の取得など、明示的に約束する配布機能は、その機能自体の検証を必要とする。「回答試験を任意にする」を理由に、壊れた配布物を合格にしない。Pack内容の合否、配布機能、モデルでの回答性能を別々に表示する。

## 6. 時間・費用を固定する方法

生成前に入力規模、資料数、PDF復元の必要性、出力上限、モデル設定から処理単位を求める。次の工程ごとに、呼出し数、入出力量、timeout、費用予約の上限を設定する。

1. 入力準備・構造確認。画像によるPDF復元が必要ならここに含める。
2. 生成。
3. 初回の直接検査と、総枠を固定した疑義の追加参照・判定。
4. 一括修正1回。
5. 再検査、最終配布物の機械検査、報告作成。

一括修正1回は、API呼出し1回と同義ではない。項目数に応じた分割数まで実行前の上限に含める。再検査と最終報告の枠を先に確保し、生成に使い切らせない。出力が膨らんでも検査呼出しを自動増額しない。

費用と期限は再開・移行後も累計で引き継ぐ。失敗や結果不明の呼出しをゼロ費用扱いにしない。CLI報告額、予約額、実際の請求額の区別は維持する。既存の各冊上限をこの案で変更しない。

この設計で予測可能になるのは、まず実行工程と最大消費枠である。完成率、通常の所要時間、通常の費用は、新方式の実測から報告する。未測定の段階で「何冊でも必ず2時間で合格する」とは主張しない。

ワークフローの実績を調べる試験は、各冊の品質検査と分ける。現行の「最低2冊・各条件2反復・3欠陥種」という検証方法を、個々のPackが合格するための条件にしない。productionの既存証明を流用せず、証明必須の経路は見直し対象として明示する。新方式の信頼性は、事前に固定した有限の制作試験で、失敗も含めて報告する。

## 7. 結果の表し方

自動検査の結果と著者承認を別の状態として保存する。単一の`failed_quality`へ全てを押し込めない。

| 直接検査の結果 | 意味 |
|---|---|
| `pass` | 必須の直接検査を完了し、確認済み欠陥と未解決の具体的疑義がない。著者承認待ちへ進める |
| `fail` | 確認済み欠陥が残っている。検査の未完了が併存する場合は併記する |
| `inconclusive` | 資料不足、判定不能、処理未完了などで合否を確定できない |
| `not_run` | 直接検査をまだ実行していない |

実行停止理由として、期限、費用、入力制約、provider障害などを別に記録する。利用試験は`not_run`または実測値を持つ独立欄とし、未実施を直接検査の不合格にしない。

合否報告には、候補と配布物のハッシュ、原資料のハッシュ、指示テンプレート版、検査基準版、検査対象と完了範囲、指摘と根拠、修正差分、未確認事項、実行資源を保存する。モデル名と検査方法も残す。自動検査の`pass`から著者承認や公開を推定しない。

## 8. 実装の変更箇所

以下は実装箇所の設計上の対応である。実際の入口・保存形式は制作ガイドを参照する。

| 箇所 | 変更内容 |
|---|---|
| `pipeline_purpose.py` | 目的契約を改訂し、Packの合否と利用モデルの診断を区別する |
| `pipeline.py` | 標準制作の設問生成・development/holdout必須経路を外し、直接検査と最大1回修正で制御する。handoffの根拠も変更する |
| `pipeline_evaluation.py` | 回答結果を診断として返す。正答率不足からPackの欠陥を自動生成しない |
| `pipeline_audit.py`、`pipeline_resolution.py` | 現行の原典照合と証拠付き判定を再利用し、指示検査、項目単位の検査完了、根拠付き欠陥、未確定状態をまとめる |
| 生成・修正・配布検査 | 共通指示の版、書籍固有の差分、原典との対応、変更の影響範囲、最終配布物の一致を扱う |
| `pipeline_resources.py` | 必須の回答・採点・holdout枠を取り除き、直接検査と再検査の枠で計画する |
| `pipeline_qualification.py` | 完成の定義を直接検査の合格と著者確認票への到達へ変更する。モデル正答率と固定試験数による個別Packの合否拘束を外す |
| `pipeline_reuse.py`、CLI、Schema | 旧方式の再開と新方式の再判定を区別し、契約と累計資源を保持する |
| 品質報告、日英文書 | 自動検査、著者承認、配布機能、モデル性能、制作実績を区別した表示へ揃える |

既存の原典監査、保護された著者資料、証拠照合、予算台帳を再利用する。新しい多段の資格取得手順を標準制作へ追加しない。共通指示テンプレートとその検査はツールの開発時に扱い、各冊の著者へ運営を求めない。

Pack内容形式を変えずに制作経路を改訂する場合、制作エンジンと検査契約を版管理する。Pack形式の互換性まで変更した扱いにはしない。正式な公開版番号は実装差分に応じて決め、この設計案だけで現在の公開版を更新しない。

## 9. 既存候補への適用

旧runの設定、判定、費用、候補を保持し、新契約による再判定を別の記録として作る。現候補を読み込む入口を用意し、本文からの全面再生成と旧設問の再実行を要求しない。

原資料、抽出済みの構造、引用照合の事実は同一性を確認して再利用する。旧基準での意味の判定を、新基準の合格証拠として自動流用しない。現在の候補に紐づく直接検査を実施し、確認済み欠陥だけを一括修正する。

旧候補は不変のまま、修正した候補に新しいハッシュを付ける。新たな再判定は旧runの期限を無断で更新しない。実行条件を明示した別の評価計画として扱い、既存の累計費用上限を引き継ぐ。予算不足や未実施は合格にも品質不合格にも読み替えない。

既存候補の再判定で分かるのは、その候補の品質である。新方式で本文から予測可能な時間・費用で生成できるかは、別の制作実測で確認する。

## 10. 実装の確認条件と順序

まず、次の失敗を検出できる合成試験を用意する。公開テストには実書籍の本文や非公開評価を入れない。

- 正しいPackに対する利用モデルの誤答が、Pack不合格へ変換されない。
- 回答が偶然正しくても、Packの捏造、条件の脱落、誤った帰属、壊れた参照を検出する。
- 空疎な章要約、共通指示と書籍固有指示の矛盾、配布時の指示欠落を検出する。
- 本文のみと著者資料ありの両方で、途中の著者操作なしに検査と確認票作成へ進む。
- 一括修正1回で停止し、再検査や疑義の判定から追加ループが生まれない。
- 検査未完了と確認済み欠陥を区別し、旧結果・承認・累計費用を維持する。

実装順序は、合否と診断の分離、直接検査の不足分、固定の一括修正と資源計画、既存候補の再判定入口、報告と文書の更新とする。変更に対応する試験とリポジトリの必須検査を実施する。

その後、既存候補を全面再生成せずに再判定する。本文のみ・著者資料ありの新規制作については、モデル・入力範囲・回数・時間・費用を固定した有限の試験計画で実測する。合格が出るまで試行数を増やさず、観測した完成率、未完了理由、費用、所要時間を報告する。

この案の直近の到達点は、ユーザーの目的に沿った合否判定と、有限の制作工程を実装可能な形で定義することである。現候補の合格、新方式の制作実績、著者承認は、それぞれ対応する証拠が得られた時点で記録する。
